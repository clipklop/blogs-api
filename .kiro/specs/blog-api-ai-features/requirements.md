# Requirements Document

## Introduction

This document specifies the requirements for Phase 5 of the Blogs API: AI-powered features. Two capabilities are introduced on top of the existing FastAPI + PostgreSQL CRUD service.

The first is an **LLM Writing Assistant** that automatically generates a plain-language summary and a set of suggested tags for each post. This enrichment runs as a background job so HTTP responses are never blocked.

The second is **Semantic Search**: a text embedding is stored for each post using pgvector, and a new search endpoint returns posts ranked by cosine similarity to a natural-language query.

Both features share a single configurable OpenAI-compatible AI provider client. All database schema changes are delivered as Alembic migrations; the legacy `Base.metadata.create_all()` startup call is removed.

---

## Glossary

- **API**: The FastAPI HTTP service defined in `main.py`.
- **Post**: The core domain object stored in the `posts` table with fields: `id`, `title`, `content`, `published`, `rating`, `created_at`, `updated_at`.
- **AI_Client**: The module (`ai_client.py`) that encapsulates all calls to an OpenAI-compatible provider, offering `generate_summary`, `suggest_tags`, and `generate_embedding` helpers.
- **Worker**: The ARQ background worker process (`worker.py`) that dequeues and executes AI enrichment jobs.
- **Job_Queue**: The ARQ + Redis task queue used to pass enrichment work from the API to the Worker.
- **Summary**: A short plain-language description of a post, generated by the LLM from `title` and `content`.
- **Tags**: A list of short keyword strings suggested by the LLM for a post, stored as a JSON array in the `tags` column.
- **Embedding**: A fixed-length float vector (`vector(1536)`) representing the semantic content of a post, stored via the pgvector extension.
- **Similarity_Score**: The cosine similarity (0–1) between a query embedding and a post embedding.
- **AI_Enrichment_Job**: A single ARQ task that calls the AI_Client to produce Summary, Tags, and Embedding for one Post, then persists the results.
- **Alembic**: The database migration tool that manages all schema changes.
- **AsyncSession**: The SQLAlchemy async session used by all routes and the Worker after the async migration.
- **pgvector**: The PostgreSQL extension that adds a native `vector` column type and cosine similarity operators.
- **Settings**: The Pydantic-Settings configuration object that exposes `ai_base_url`, `ai_api_key`, `ai_chat_model`, `ai_embedding_model`, and `ai_embedding_dimensions`.

## Requirements

---

### Requirement 1: Async Database Layer Migration

**User Story:** As a developer, I want all database I/O to use async SQLAlchemy sessions, so that the API can handle concurrent AI-enrichment callbacks and background tasks without blocking the event loop.

#### Acceptance Criteria

1. THE API SHALL use `AsyncSession` for all database reads and writes.
2. THE API SHALL expose all route handler functions as `async def`.
3. WHEN the API starts, THE API SHALL establish the async SQLAlchemy engine using the existing `DATABASE_URL` setting without requiring a new environment variable.
4. IF the async database connection cannot be established within `database_connect_timeout` seconds (default: 30 seconds, minimum: 1 second, maximum: 300 seconds), THEN THE API SHALL refuse to start and emit a startup error message indicating that the database connection failed and identifying the configured timeout value.
5. THE API SHALL return responses with the same HTTP status codes and the same top-level response body fields for all existing CRUD endpoints as before the async migration.

---

### Requirement 2: Alembic Migration Infrastructure

**User Story:** As a developer, I want all schema changes to be delivered as Alembic migrations, so that database evolution is reproducible, reversible, and safe in any environment.

#### Acceptance Criteria

1. THE API SHALL not contain any `Base.metadata.create_all()` call in application startup code.
2. THE Alembic configuration SHALL read `DATABASE_URL` from the same environment variable used by the API, without duplicating the value.
3. WHEN `alembic upgrade head` is run against a fresh (empty) database, THE Alembic migration SHALL create all tables and columns defined in the SQLAlchemy models without errors, and each table and column defined in the models SHALL exist in the database after the migration completes.
4. WHEN `alembic downgrade -1` is run on a database that contains at least one post row, THE Alembic migration SHALL revert the schema to the state before that migration was applied, all pre-existing post rows SHALL still exist, and no column defined only in the downgraded migration SHALL remain in the database.
5. THE Alembic migration history SHALL include one baseline migration that documents the initial `posts` table schema with the following columns: `id`, `title`, `content`, `published`, `rating`, `created_at`, `updated_at`.

---

### Requirement 3: AI Column Schema

**User Story:** As a developer, I want the `posts` table to store AI-generated fields, so that enrichment results are persisted alongside the post and available to the API without re-calling the AI provider.

#### Acceptance Criteria

1. THE Alembic migration SHALL add the following columns to the `posts` table, each nullable with a database-level default of NULL: `summary` (Text), `tags` (JSONB), `embedding` (vector of dimension equal to `ai_embedding_dimensions`, default 1536), `ai_processed_at` (timestamp with timezone).
2. WHEN a post is created via `POST /posts/`, THE API SHALL not include `summary`, `tags`, `embedding`, or `ai_processed_at` in the INSERT statement payload, relying on the database-level NULL defaults for those columns.
3. THE `posts` table SHALL have an HNSW index on the `embedding` column using `vector_cosine_ops` after the migration applies.
4. WHEN `alembic downgrade -1` is run on the migration that added the AI columns, THE migration SHALL drop the `summary`, `tags`, `embedding`, and `ai_processed_at` columns and the HNSW index on `embedding` without error, and those columns and index SHALL not exist in the database afterward.
5. WHERE `ai_embedding_dimensions` is set to a value other than 1536 in application configuration, THE Alembic migration SHALL define the `embedding` column as `vector(<ai_embedding_dimensions>)` using that configured value.

---

### Requirement 4: AI Provider Client

**User Story:** As a developer, I want a single configurable AI client module, so that I can switch AI providers (OpenAI, LiteLLM, Ollama, vLLM, OpenRouter) by changing settings without modifying application code.

#### Acceptance Criteria

1. THE Settings SHALL expose `ai_base_url` (str, required), `ai_api_key` (str, default empty string), `ai_chat_model` (str, required), `ai_embedding_model` (str, required), and `ai_embedding_dimensions` (int, default 1536) as environment-variable-backed fields.
2. WHEN `generate_summary`, `suggest_tags`, or `generate_embedding` is called with an empty or whitespace-only input string, THE AI_Client SHALL raise a `ValueError` before making any network request.
3. WHEN `generate_summary` is called with a non-empty post title and content, THE AI_Client SHALL send a chat completion request to `{ai_base_url}/v1/chat/completions` with the `Authorization: Bearer {ai_api_key}` header included only if `ai_api_key` is non-empty, and SHALL return a non-empty string.
4. WHEN `suggest_tags` is called with a non-empty post title and content, THE AI_Client SHALL send a chat completion request to `{ai_base_url}/v1/chat/completions` and SHALL return a list of 1–10 strings where each string matches the pattern `[a-z][a-z0-9]*(-[a-z0-9]+)*`.
5. WHEN `generate_embedding` is called with a non-empty text string, THE AI_Client SHALL send an embeddings request to `{ai_base_url}/v1/embeddings` and SHALL return a list of floats whose length equals `ai_embedding_dimensions`.
6. WHEN any AI_Client method makes a request and no response is received within 30 seconds, THE AI_Client SHALL raise an `AIProviderError` with a message indicating a timeout.
7. IF the AI provider returns an HTTP 4xx or 5xx response to any request, THEN THE AI_Client SHALL raise an `AIProviderError` containing the HTTP status code and the raw response body text.
8. IF the AI provider returns an HTTP 2xx response to a `generate_summary` call but the response body cannot be parsed to extract a non-empty string, THEN THE AI_Client SHALL raise an `AIProviderError` with a message identifying the parsing failure.
9. IF the AI provider returns an HTTP 2xx response to a `suggest_tags` call but the response body cannot be parsed to extract a list of strings, THEN THE AI_Client SHALL raise an `AIProviderError` with a message identifying the parsing failure.
10. IF the AI provider returns an HTTP 2xx response to a `generate_embedding` call but the response body cannot be parsed to extract a list of floats of the expected length, THEN THE AI_Client SHALL raise an `AIProviderError` with a message identifying the parsing failure.
11. FOR ALL non-empty text strings `t`, `cosine_similarity(generate_embedding(t), generate_embedding(t))` SHALL equal 1.0 (round-trip identity property).

### Requirement 5: ARQ Background Worker

**User Story:** As a developer, I want AI enrichment to run as a background job, so that HTTP responses for post create and update operations are not delayed by AI provider latency.

#### Acceptance Criteria

1. THE Worker SHALL connect to Redis using the `REDIS_URL` setting exposed in Settings (default: `redis://localhost:6379`).
2. THE Docker Compose configuration SHALL include a `redis` service using the `redis:7-alpine` image.
3. WHEN an AI_Enrichment_Job is dequeued, THE Worker SHALL call `generate_summary`, `suggest_tags`, and `generate_embedding` for the target post and write the results to the `summary`, `tags`, `embedding`, and `ai_processed_at` columns in a single atomic database transaction; if the transaction fails, no partial result SHALL be persisted.
4. WHEN an AI_Enrichment_Job completes successfully, THE Worker SHALL set `ai_processed_at` to the current UTC timestamp on the target post within the same transaction that persists the AI results.
5. IF the target post does not exist in the database when an AI_Enrichment_Job is dequeued, THEN THE Worker SHALL log a warning containing the post ID and return without error and without retrying.
6. IF the AI_Client raises an `AIProviderError` during an AI_Enrichment_Job, THEN THE Worker SHALL retry the full job (all three AI calls) up to 3 additional times using exponential back-off with a base delay of 1 second, a multiplier of 2, and a maximum delay of 60 seconds between retries.
7. IF all 3 retries of an AI_Enrichment_Job are exhausted without success, THEN THE Worker SHALL log an error containing the post ID and the final `AIProviderError` message, and SHALL leave `ai_processed_at` as NULL on that post.
8. IF a database error occurs while persisting AI results during an AI_Enrichment_Job, THEN THE Worker SHALL roll back the transaction, log the error with the post ID, and NOT retry the job.
9. THE Docker Compose configuration SHALL include a `worker` service that starts the ARQ worker process pointing at the `WorkerSettings` class in `blogs_api.worker`.

### Requirement 6: Automatic AI Enrichment on Post Write

**User Story:** As a developer, I want AI enrichment to be triggered automatically when a post is created or its content changes, so that the Summary, Tags, and Embedding are always up to date without manual intervention.

#### Acceptance Criteria

1. WHEN a post is created via `POST /posts/`, THE API SHALL enqueue an AI_Enrichment_Job for that post's ID before returning the HTTP 201 response.
2. WHEN a `PATCH /posts/{post_id}` request is processed and the new value of `title` differs from the stored value OR the new value of `content` differs from the stored value, THE API SHALL enqueue an AI_Enrichment_Job for that post's ID before returning the HTTP 200 response.
3. WHEN a `PATCH /posts/{post_id}` request is processed and neither `title` nor `content` is present in the request body, OR both are present but their values are identical to the stored values, THE API SHALL NOT enqueue an AI_Enrichment_Job.
4. IF enqueuing an AI_Enrichment_Job raises an exception (e.g. Redis is unreachable), THEN THE API SHALL log the exception including the post ID and return the normal HTTP response to the caller without surfacing the error to the client.
5. THE `PostResponse` schema SHALL include `summary` (string or null), `tags` (array of strings or null), and `ai_processed_at` (ISO 8601 datetime string or null) in the HTTP response body.
6. THE `PostResponse` schema SHALL NOT include an `embedding` field in any HTTP response body.

---

### Requirement 7: AI Enrichment Status Endpoint

**User Story:** As a developer, I want to inspect the AI enrichment status of a post, so that I can determine whether enrichment has completed, is pending, or has failed.

#### Acceptance Criteria

1. THE API SHALL expose a `GET /posts/{post_id}/ai-status` endpoint that accepts a positive integer `post_id` path parameter.
2. WHEN `GET /posts/{post_id}/ai-status` is called for a post whose `ai_processed_at` column is not NULL, THE API SHALL return HTTP 200 with a JSON body containing `"status": "done"` and `"ai_processed_at"` set to the timestamp in ISO 8601 UTC format (e.g. `"2024-01-15T10:30:00Z"`).
3. WHEN `GET /posts/{post_id}/ai-status` is called for a post whose `ai_processed_at` column is NULL (covering both awaiting-first-enrichment and permanently-failed states), THE API SHALL return HTTP 200 with a JSON body containing `"status": "pending"` and no `ai_processed_at` field.
4. IF `GET /posts/{post_id}/ai-status` is called with a `post_id` that does not correspond to any row in the `posts` table, THEN THE API SHALL return HTTP 404 with a JSON body containing a `"detail"` field that identifies the missing post ID.

---

### Requirement 8: Manual AI Re-Processing Endpoint

**User Story:** As a developer, I want to manually trigger AI re-processing for a single post, so that I can recover from failed enrichment jobs without redeploying or patching the post content.

#### Acceptance Criteria

1. THE API SHALL expose a `POST /posts/{post_id}/regenerate-ai` endpoint that accepts a positive integer `post_id` path parameter.
2. WHEN `POST /posts/{post_id}/regenerate-ai` is called for a post that exists, THE API SHALL enqueue an AI_Enrichment_Job for that post's ID without modifying any AI fields on the post immediately, and SHALL return HTTP 202 with `{"status": "queued", "post_id": <id>}`.
3. IF `POST /posts/{post_id}/regenerate-ai` is called with a `post_id` that does not correspond to any row in the `posts` table, THEN THE API SHALL return HTTP 404 with a JSON body containing a `"detail"` field that identifies the missing post ID.
4. WHEN `POST /posts/{post_id}/regenerate-ai` is called for a post that already has `ai_processed_at` set, THE API SHALL enqueue the job and return HTTP 202; upon job completion the Worker SHALL overwrite the existing `summary`, `tags`, `embedding`, and `ai_processed_at` values.
5. IF enqueuing the AI_Enrichment_Job raises an exception, THEN THE API SHALL return HTTP 503 with `{"detail": "Job queue unavailable"}`.

---

### Requirement 9: Bulk AI Backfill Endpoint

**User Story:** As a developer, I want to trigger AI enrichment for all posts that have not yet been processed, so that historical posts are enriched when the AI feature is first deployed.

#### Acceptance Criteria

1. THE API SHALL expose a `POST /posts/backfill-ai` endpoint.
2. WHEN `POST /posts/backfill-ai` is called and at least one post has `ai_processed_at` equal to NULL, THE API SHALL enqueue one AI_Enrichment_Job per such post and return HTTP 202 with `{"queued": <count>}` where `<count>` equals the number of jobs successfully enqueued.
3. WHEN `POST /posts/backfill-ai` is called and every post in the `posts` table has `ai_processed_at` set to a non-NULL value, THE API SHALL return HTTP 202 with `{"queued": 0}` without enqueuing any jobs.
4. THE API SHALL retrieve posts eligible for backfill in batches of at most 100 rows per database query, processing all batches before returning the response.
5. IF one or more enqueue calls fail during a backfill operation, THE API SHALL continue processing remaining posts, and the `queued` count in the response SHALL reflect only the number of jobs successfully enqueued.

### Requirement 10: Semantic Search Endpoint

**User Story:** As a reader, I want to search for posts using natural language, so that I can find semantically relevant posts even when the exact words do not appear in the title or content.

#### Acceptance Criteria

1. THE API SHALL expose a `GET /posts/search` endpoint that accepts a required `q` query parameter of 1–500 characters; if `q` is absent, empty, or exceeds 500 characters, THE API SHALL return HTTP 422 with a descriptive validation error.
2. WHEN `GET /posts/search?q=<query>` is called with a valid `q`, THE API SHALL call `generate_embedding` on `q`, query the `posts` table ordered by ascending cosine distance to the query embedding (descending similarity), and use ascending `id` as a tie-breaker for posts with equal cosine distance.
3. THE `GET /posts/search` endpoint SHALL accept an optional `min_score` query parameter (float, 0.0–1.0, default 0.0); if `min_score` is outside [0.0, 1.0], THE API SHALL return HTTP 422.
4. THE `GET /posts/search` endpoint SHALL accept optional `limit` (int, 1–100, default 20) and `offset` (int, ≥ 0, default 0) query parameters; if either is outside its valid range, THE API SHALL return HTTP 422.
5. WHEN `GET /posts/search` is called, THE API SHALL exclude any post whose `embedding` column is NULL from the result set before applying similarity scoring.
6. EACH item in the search results SHALL include a `score` field whose value is `1.0 - cosine_distance(query_embedding, post_embedding)`, rounded to 6 decimal places, alongside all fields present in `PostResponse`.
7. IF the AI_Client raises an `AIProviderError` while embedding the query `q`, THEN THE API SHALL return HTTP 502 with `{"detail": "AI provider unavailable"}`.
8. FOR ALL valid query strings `q`, calling `GET /posts/search?q=<q>` twice in succession SHALL return the same list of post IDs in the same order, provided no posts are inserted, updated, or deleted between the two calls.
9. WHERE `min_score` is provided, THE API SHALL include in the result only posts whose `score` field value satisfies `score >= min_score`.

---

### Requirement 11: Semantic Search Correctness Properties

**User Story:** As a developer, I want the embedding and similarity logic to be verifiable, so that I can be confident semantic search returns relevant results and ranks them correctly.

#### Acceptance Criteria

1. FOR ALL posts `p` whose `embedding` column is not NULL, `1.0 - cosine_distance(p.embedding, p.embedding)` SHALL equal 1.0 (self-similarity invariant).
2. GIVEN a fixed query embedding `q_vec`, a post `a` with embedding `e_a`, and a post `b` with embedding `e_b`, WHERE `1.0 - cosine_distance(e_a, q_vec) > 1.0 - cosine_distance(e_b, q_vec)` holds in the database, THEN post `a` SHALL appear before post `b` in the results of `GET /posts/search?q=<q>` (ranking consistency property).
3. FOR ALL valid `q` and positive integer `N` ≤ 100, the set of post IDs returned by `GET /posts/search?q=<q>&limit=N` SHALL be a subset of the post IDs returned by `GET /posts/search?q=<q>&limit=100` (subset invariant).
4. FOR ALL items in any non-empty search result set, the `score` field SHALL satisfy `0.0 ≤ score ≤ 1.0` (range invariant).
5. WHEN `GET /posts/search` is called with `min_score=1.0` and the database contains posts whose embeddings were NOT generated from the query string itself, THE API SHALL return an empty result list.

### Requirement 12: AI Feature Test Coverage

**User Story:** As a developer, I want automated tests for all AI-related behaviour, so that regressions are caught before deployment.

#### Acceptance Criteria

1. THE test suite SHALL use `pytest-asyncio` with `asyncio_mode = "auto"` and `httpx.AsyncClient` over `ASGITransport` for all API integration tests introduced in this phase.
2. THE test suite SHALL include a test that creates a post via `POST /posts/` and asserts that exactly one AI_Enrichment_Job enqueue call was made with the correct post ID.
3. THE test suite SHALL include a test that updates a post's `content` via `PATCH /posts/{id}` with a new value and asserts that exactly one AI_Enrichment_Job enqueue call was made.
4. THE test suite SHALL include a test that sends a `PATCH /posts/{id}` request updating only `published` or only `rating` and asserts that zero AI_Enrichment_Job enqueue calls were made.
5. THE test suite SHALL include separate tests for `GET /posts/{post_id}/ai-status` returning `"done"` (post has `ai_processed_at` set), `"pending"` (post has `ai_processed_at` NULL), and HTTP 404 (post does not exist).
6. THE test suite SHALL include tests for `POST /posts/{post_id}/regenerate-ai` covering: success returns HTTP 202 with correct body, post not found returns HTTP 404, and enqueue failure returns HTTP 503.
7. THE test suite SHALL include tests for `POST /posts/backfill-ai` covering: mixed state returns HTTP 202 with correct queued count, all-processed state returns HTTP 202 with `{"queued": 0}`.
8. THE test suite SHALL include tests for `GET /posts/search` covering: valid query returns posts in descending score order, `min_score` filter excludes posts below threshold, `q` exceeding 500 characters returns HTTP 422, and `AIProviderError` on embedding returns HTTP 502.
9. THE test suite SHALL mock `generate_summary`, `suggest_tags`, and `generate_embedding` in all tests that do not specifically exercise AI provider connectivity, using fixed deterministic return values (e.g. `generate_embedding` returns a fixed list of 1536 floats with value 1.0/√1536).
10. THE test suite SHALL include a property test asserting that `cosine_similarity(generate_embedding(t), generate_embedding(t)) == 1.0` for at least 10 distinct non-empty text strings `t`, using mocked embeddings that are deterministic unit vectors.
11. THE test suite SHALL include a test that mocks the ARQ Worker context and calls `process_post_ai` directly, asserting that after 3 failed AI calls the post's `ai_processed_at` remains NULL and the error is logged.
